| 想定環境 | Windows、Windows PowerShell 5.1、Microsoft Edge、Microsoft 365の職場または学校アカウント |

## 1. 結論

「操作を記録して手順にする」は、DOM、UI Automation、MSAAなどで操作対象を確定する機能から、次の機能へ作り替える。

> クリック位置と操作前後の画面を正確に記録し、すべての操作をMicrosoft 365 Copilotで解析して、手順候補へ変換する機能

記録用Edgeは廃止する。利用者は、普段使用しているEdge、ファイルエクスプローラー、Excel、社内アプリなどをそのまま操作する。

Microsoft 365 Copilot Chatには公開APIがないため、Copilot連携は専用EdgeプロファイルをChrome DevTools Protocol（CDP）で操作する現在の方式を継続する。これは公式APIではないため画面変更の影響を受けるが、本機能の必須経路として設計し、変更検知、自己診断、再試行、途中再開、診断情報の保存を組み込む。

DOM、UI Automation、MSAA、OCR、画像輪郭検出は正解を決めるために使わない。Copilotへ提示する赤枠候補を作る補助手段へ格下げする。

Copilotの回答をそのまま確定値として取り込まない。全件を確認画面へ出し、利用者が採用、除外、赤枠修正、文章修正できるようにする。

## 2. 背景と問題

### 2.1 現行方式で起きている問題

現行の操作記録は、クリック時にDOM、UI Automation、MSAAなどから対象名と矩形を取得し、その場で赤枠と切り抜き範囲を確定する。

この方式では、次の問題を解消できていない。

- Webページ、ファイルエクスプローラー、Office、旧式アプリ、独自描画アプリで取得可能な情報が異なる
- ページ遷移やダイアログ表示がクリックより速いと、対象情報と画像の時点がずれる
- DPI、拡大率、マルチモニター、ブラウザー表示倍率によって座標変換が複雑になる
- UI Automationがページ全体や親コンテナーを返す場合がある
- DOMを正確に取得するための記録用Edgeは、普段のログイン、ブックマーク、拡張機能、プロファイルと分かれ、利用しづらい
- 誤った対象を先に確定すると、赤枠、切り抜き、Copilotへの添付画像まで連鎖して誤る
- 例外処理を追加するほど、対象判定、画像時点、ウィンドウ照合の分岐が増える

### 2.2 根本原因

根本原因は検出器の種類が不足していることではない。異なる画面技術を横断して、クリック時点で唯一の正解矩形を確定することを製品要件にしている点にある。

新方式では、記録時の責務を「正確な証拠の保存」に限定し、対象の意味付けを記録後のCopilot解析へ移す。

## 3. 設計上の決定

| ID | 決定 |
|---|---|
| D-01 | 記録用Edgeを廃止する |
| D-02 | Copilot制御用の専用Edgeプロファイルは残す |
| D-03 | 利用者のすべての記録対象操作をCopilotへ送る。低信頼時だけ送る方式にはしない |
| D-04 | クリック位置と時刻を記録の確定事実とする |
| D-05 | 元画像は加工せず保存し、赤枠、マーカー、切り抜きは派生情報として保持する |
| D-06 | DOM、UIA、MSAAなどは候補生成にだけ使う |
| D-07 | Copilotは候補選択、操作要否判定、対象名、文章作成を担う |
| D-08 | Copilot解析が終わらなくても記録データを失わず、後から再開できる |
| D-09 | Copilotへ送る画像の黒塗りは自動化せず、必要な場合に利用者が手動で指定する |
| D-10 | Copilotの特定モデル名に依存しない。画像理解可能な現在のモデルを使う |
| D-11 | AI回答だけを理由に記録を完全削除しない。不要候補は未選択状態で残す |
| D-12 | CopilotのUI変更対応を一つのアダプターへ隔離する |

## 4. 対象範囲

### 4.1 本仕様の対象

- 左クリック
- 右クリック
- 入力欄への一連の文字入力
- クリック前後の画面取得
- 意味のない空クリックの候補除外
- 操作対象の名称と範囲の推定
- 初期切り抜き範囲の算出
- 手順名、説明、補足の下書き
- Copilotへの画像添付とプロンプト送信
- 回答解析、検証、再試行、途中再開
- Copilotへ送る前の手動黒塗り
- 結果確認とプロジェクトへの取り込み

### 4.2 本仕様の対象外

- APIを使用したCopilot連携
- Copilot Studioエージェントの作成
- 操作中のリアルタイムCopilot解析
- キー入力した文字列そのもののキーロガー形式での保存
- Copilotの回答を無確認で正式手順へ確定すること
- Copilotへアップロード済みのOneDriveファイルや会話を自動削除すること
- リモートデスクトップ先の内部UI構造の取得
- オフライン状態での手順文章自動生成

## 5. Microsoft 365 Copilotの前提確認

本節は2026-08-04時点のMicrosoft公式情報に基づく。サービス側の変更があり得るため、実装値ではなく外部依存条件として管理する。

### 5.1 確認済み事項

| 項目 | 確認内容 | 設計への反映 |
|---|---|---|
| 画像入力 | Copilot Chatは画像のアップロード、コピー、貼り付けをプロンプトで利用できる | 操作前後画像を添付して解析する |
| ローカル画像 | ローカルから選択した画像のコピーはOneDriveへ保存される | クラウドへ残ることを送信前に明示する |
| API | Copilot Chatの公開APIは提供されていない | CDPによる画面操作を必須経路とする |
| アカウント | 職場または学校のMicrosoft 365アカウントで利用する | 個人向けCopilotへ誤送信しないようホストと画面を確認する |
| データ保護 | EntraアカウントではEnterprise Data Protectionが適用され、プロンプトと回答は基盤モデルの学習に使われない | 職場アカウントのみを前提とする |
| 監査 | プロンプトと回答はログ、保持、監査、eDiscoveryの対象になり得る | 利用者へ会話が一時処理だけではないことを示す |
| DLP | プロンプトへ直接アップロードしたファイルの中身はPurview DLPで検査されない | アプリ側の送信前確認と手動黒塗りを必須にする |
| 非決定性 | 同じプロンプトでも異なる回答になることがある | 回答検証、再試行、人による確認を必須にする |
| 可用性 | ライセンスにより標準アクセスと優先アクセスがあり、標準アクセスは混雑時に制限され得る | タイムアウト、待機、再開を前提とする |
| 正確性 | Microsoft自身がCopilot出力の検証を求めている | 自動確定せず確認画面を置く |

### 5.3 固定値として扱わない事項

次の項目はMicrosoftが変更できるため、コードへ固定しない。

- モデル名
- モデル選択ボタンの表示有無
- Copilot ChatのURLパス
- 入力欄、添付欄、送信ボタン、停止ボタンのCSSセレクター
- 画像添付件数の実用上限
- 添付完了時の表示文言
- 回答領域のDOM構造
- 標準アクセス時の待ち時間

本仕様では、初期値を設定ファイルに持たせ、意味的探索と画面状態検証を併用する。

### 5.4 現行Copilot実装の確認結果

GitHub上の現行 `main` を確認したところ、Copilot連携には次の基盤がすでにある。

- APIキーやGraph権限を使わず、専用EdgeプロファイルをCDPで操作する
- 既定URLは `https://m365.cloud.microsoft/chat/`
- Edgeを画面外または最小化してもタイマーを止めない起動オプション
- CDPターゲットの再探索とサインイン画面への遷移対応
- 設定ファイルから差し替えられるセレクター
- CSSセレクターに加え、表示文言やアクセシビリティ名を使った入力、添付、送信、新規チャットの探索
- `DOM.setFileInputFiles` による画像添付
- 添付完了と添付失敗の待機
- プロンプトの分割入力と入力文字数確認
- モデル候補を優先順に試し、選べなくても現在モデルで続ける処理
- 終了マーカーと生成停止を使った回答完了判定
- コードフェンスや一部崩れたJSONからの回答抽出、修復
- 別プロセスのCopilotジョブ、進捗、中止、結果保存
- サインイン用Copilot画面を前面へ出す機能

この基盤は新方式でも再利用する。ただし、現在の契約は次の点で新方式に適合しない。

| 現行仕様 | 問題 | 新仕様 |
|---|---|---|
| 1回の依頼で既定6手順 | 画像と操作の対応をCopilotが取り違える可能性がある | 初期実装は1操作1チャット |
| 赤枠を焼き込んだ画像だけを添付 | 誤った赤枠がCopilotの判断を誘導する | 元の文脈画像、クリック周辺、操作後画像を添付 |
| 「赤枠は推測ではない」と明記 | 現在の実態と反し、誤判定を強化する | クリック点だけを事実、枠は候補と明記 |
| 回答はkeep、title、description、note中心 | 対象範囲をCopilotが修正できない | candidateId、bbox、対象名、種類、要確認を追加 |
| 手順パケット単位の進捗 | 途中中断時の再送範囲が大きい | イベント単位で原子的にチェックポイント保存 |
| 固定モデル候補名を設定 | モデル名や提供状況が変わる | 合成画像の自己診断結果を採用条件にする |
| `main` の表示テキストから回答を探索 | UI変更やプロンプト表示の混入を受ける | 会話ターン、送信時刻、終了マーカーを組み合わせる |

現行実装はゼロから作り直す必要はない。ただし、プロンプト、添付画像、回答スキーマ、ジョブ単位は全面的に変更する。

### 5.5 Copilot採用可否の結論

Microsoft 365 Copilot Chatは、画像を添付して内容について質問できるため、本方式の意味判定には利用できる。一方、Microsoftは画面上のクリック点からピクセル単位の矩形を安定して返す機能や、その精度を保証していない。

したがって、Copilot採用の結論は次のとおりとする。

- 操作の意味、対象名、手順要否、説明文はCopilotを主判定者とする
- 幾何情報はローカル候補からの選択を優先する
- Copilotの自由座標は候補がない場合だけ使い、必ず要確認にする
- Copilotが対象を決められない場合は、誤枠を付けずクリック位置だけを残す
- Copilotを必須経路とするが、Copilot回答を無検証の確定値にはしない

CDPによる画面操作は、公開APIに基づく安定した統合ではない。これは本仕様で受容する製品リスクであり、自己診断とアダプター保守を継続することが本機能の運用条件となる。

## 6. 利用者の操作フロー

### 6.1 初回準備

1. ManualBuilder起動と同時に、アプリがCopilot制御用Edgeを通常ウィンドウで準備する。
2. ManualBuilderはEdgeの準備を待たずに利用できる。
3. サインインが必要な場合、利用者が表示された画面で職場または学校アカウントへサインインする。
4. ManualBuilderのヘッダーへ「準備中／準備完了／サインイン必要／再起動」を表示する。
5. 解析開始時、アプリが合成テスト画像を使って画像添付、プロンプト送信、回答取得を自己診断する。

記録対象Webサイトを開くための専用Edgeは起動しない。

### 6.2 記録

1. 利用者がManualBuilderで対象シートを選ぶ。
2. 「操作を記録」を押す。
3. 送信対象とプライバシーに関する短い説明を確認する。
4. 普段使用しているアプリへ移動し、作業する。
5. 左クリック、右クリック、入力操作を記録する。
6. 記録を停止する。

記録中はCopilotへ送信しない。操作への遅延と業務中の画面切替を防ぐ。

### 6.3 送信前確認

1. 記録した操作を一覧表示する。
2. 明らかに不要な操作を利用者が除外できる。
3. Copilotへ送れない情報がある場合、画像編集で手動黒塗りする。
4. 「Copilotで解析」を押す。

黒塗りを行わない選択も可能とする。入力欄の文字が手順上必要な場合はそのまま残せる。

### 6.4 Copilot解析

1. アプリがCopilot接続を事前確認する。
2. 1操作ずつ、新しいチャットで画像とプロンプトを送る。
3. 解析結果を操作単位で保存する。
4. 中断した場合、未処理の操作から再開する。
5. 全件終了後に結果確認画面を開く。

### 6.5 結果確認と取り込み

各操作について次を表示する。

- クリック前画像
- クリック後画像
- Copilotが選んだ赤枠候補
- 操作対象名
- 手順として残すか
- 手順名
- 説明
- 補足
- Copilotの判定理由
- 「要確認」の有無

利用者は複数選択して一括採用、一括除外、別シート移動、削除ができる。赤枠は画像編集で修正できる。

## 7. 記録エンジン

### 7.1 クリック検出

現在の60Hzポーリング中心の方式から、低レベルマウスフック `WH_MOUSE_LL` を使う方式へ変更する。

フック内では次の最小情報だけをキューへ書き込む。

- クリック種別
- 物理スクリーン座標
- 高精度時刻
- ボタン押下または解放

フック内でスクリーンショット、UI Automation、ファイル書き込みを行わない。重い処理によってWindowsからフックを解除されることを防ぐ。

### 7.2 クリック前画像リングバッファ

ページ遷移前の画面を専用Edgeなしで確実に残すため、記録中だけアクティブウィンドウ画像の短いリングバッファをメモリ上に持つ。

初期値は次のとおりとする。

| 項目 | 初期値 |
|---|---:|
| 取得間隔 | 80～120ms |
| 保持時間 | 1.0秒 |
| 保持場所 | メモリのみ |
| 保存対象 | クリック直前として採用された1枚 |

クリックイベントを受けたとき、クリック時刻以前で最も新しい画像をクリック前画像として保存する。

リングバッファ内の不採用画像はファイルへ書き出さず破棄する。

### 7.3 クリック後画像

クリック後250～500msを初期値として、同じウィンドウまたは新たな前面ウィンドウを撮影する。

ページ読み込みが続く場合でも長時間待たず、操作直後の結果確認材料として扱う。必要に応じて1,000ms後の補助画像を追加できるが、初期実装では必須にしない。

### 7.4 入力操作

文字入力は個々のキーを保存しない。入力開始から一定の無操作時間までを一つの入力イベントとしてまとめる。

保存するのは次の情報だけとする。

- 入力開始前画像
- 入力終了後画像
- 入力開始時と終了時のウィンドウ
- 入力イベントであること

パスワードを含む入力文字列をキーイベントから復元しない。画面上に表示された文字は画像へ含まれる可能性があるため、送信前の手動黒塗りで対応する。

### 7.5 ウィンドウ情報

各イベントに次を保存する。

- ウィンドウハンドル
- ウィンドウタイトル
- プロセス名
- ウィンドウの物理座標とサイズ
- モニター識別子
- DPI
- クリック位置のウィンドウ内相対座標

ウィンドウタイトルやプロセス名は補助情報であり、Copilotの対象判定を上書きする確定値にはしない。

### 7.6 取りこぼし防止

- 左クリックと右クリックを記録する
- 短いクリックをフックで捕捉する
- 最大イベント数と最大記録時間を設定する
- キューが詰まった場合もクリック時刻と座標を優先して残す
- 画像取得失敗時はイベント自体を捨てず、「画像取得失敗」として確認一覧へ残す
- 同じ画面でもクリック位置が違えば別イベントとして残す

## 8. 画像と候補の生成

### 8.1 保存する原本

各イベントの原本として、クリック前のアクティブウィンドウ画像を保存する。

- 元画像へ赤枠、クリックマーカー、黒塗りを直接描き込まない
- PNGを基本とする
- 4Kなど非常に大きい画面でも、元画像は可能な限りネイティブ解像度で保持する
- 出力容量警告は既存の画像容量要件に従う

### 8.2 Copilot用派生画像

1操作につき、既定で次の3画像を生成する。

| ファイル | 内容 |
|---|---|
| `before-context.png` | クリック前のウィンドウ全体。クリック位置を小さなマーカーで表示 |
| `before-detail.png` | クリック周辺を元画像から等倍で切り出し、候補枠A～Hを表示 |
| `after-context.png` | クリック後の画面。必要な手動黒塗りを反映 |

クリックマーカーは対象文字を覆わない形にする。中心を塗りつぶさず、四方向の短い線またはリングで示す。

詳細画像は拡大補間しない。元画像のネイティブ画素から800～1,200px程度を切り出す。画面端では範囲を内側へ移動する。

### 8.3 手動黒塗り

Copilotへ送る画像は、プロジェクト上の黒塗り注釈を焼き込んだ派生画像とする。

- 元画像は変更しない
- 黒塗り範囲の画素は派生画像上で完全に不透明な色へ置換する
- 単なるぼかしを機密マスクとして扱わない
- Copilotへ添付するファイルを開き直し、黒塗りが焼き込まれていることを自己検査する

### 8.4 赤枠候補

候補は正解ではなく、Copilotが選ぶための選択肢とする。

候補源は次のとおりとする。

1. DOM候補。通常のEdgeへCDP接続しないため、原則として使用しない
2. UI Automationのクリック点周辺候補
3. MSAAのクリック点周辺候補
4. Windows OCRの文字矩形と周辺領域
5. 画像輪郭、境界線、塗り分けから得た矩形
6. クリック点を中心とした小領域

候補作成ルール:

- クリック点を含む、または一定距離以内の候補に限定する
- ウィンドウ全体、Document、Paneなど過大な候補を除外する
- 重なりが大きい候補は統合する
- 小さい候補から最大8件をA～Hで表示する
- 候補がない場合もクリック位置は必ず表示する
- 候補の出典と座標はCopilotへ送るプロンプトには書かなくてよい

## 9. Copilot連携アーキテクチャ

### 9.1 構成

```text
記録データ
   ↓
送信前確認・手動黒塗り
   ↓
Copilot解析ジョブ
   ├─ Evidence Builder    派生画像・候補画像の作成
   ├─ Copilot Adapter     Edge/CDPによる画面操作
   ├─ Prompt Builder      依頼文と回答契約
   ├─ Response Parser     JSON抽出・修復
   ├─ Result Validator    候補・座標・文字数の検証
   └─ Job Store           状態・結果・再開点の保存
   ↓
結果確認
   ↓
プロジェクトへ取り込み
```

CopilotのDOM操作コードは `ManualBuilder.Copilot.psm1` 相当の一モジュールへ限定する。録画、プロジェクト、UI側へCopilotのCSSセレクターを分散させない。

### 9.2 Copilot制御用Edge

記録用Edgeとは別物として、Copilot制御用Edgeを残す。

- 専用プロファイルで職場アカウントのサインイン状態を保持する
- 普段のEdgeを閉じることを要求しない
- 普段のWeb操作には使用しない
- CDPポートはlocalhostだけで待ち受ける
- Copilot以外のページを自動操作しない
- 起動時から通常ウィンドウで表示し、サインイン切れや停止を利用者が確認できるようにする
- 解析中に利用者がCopilot画面を操作しないよう案内する
- Copilot制御用Edgeの操作はManualBuilderの操作記録へ含めない

### 9.3 Copilotアダプターの責務

- Edgeの起動とCDP接続
- 対象ページの特定
- Copilot画面の状態取得
- 新しいチャットの開始
- 画像添付
- 添付完了確認
- プロンプト入力
- 送信
- 生成中判定
- 回答領域の取得
- 生成停止
- 画面診断情報の保存

### 9.4 セレクター戦略

次の順序で対象を探索する。

1. 設定ファイルの既知セレクター
2. `role`、`aria-label`、`title`、表示文言による意味的探索
3. 同一オリジンiframe内の探索
4. 複数候補の可視性、活性状態、周辺文脈による絞り込み
5. 対象が一意に定まらない場合は操作せず診断停止

「送信」「添付」などの単語を含む最初の要素を無条件にクリックしない。クリック後に期待した画面状態へ変わったことを必ず確認する。

### 9.5 事前自己診断

Copilotが必須経路になるため、実画像を送る前に自己診断を実行する。

自己診断は次を確認する。

1. CDPへ接続できる
2. 最終ホストが許可されたMicrosoft 365 Copilotのホストである
3. サインイン済みである
4. チャット入力欄が見える
5. 添付欄が見つかる
6. 合成テスト画像を添付できる
7. 固定テストプロンプトを送信できる
8. 終了マーカー付きJSON回答を取得できる
9. 候補選択の簡単な画像問題へ正答できる

自己診断用画像には業務情報を含めない。例えばA、B、Cの3ボタンとクリックマーカーだけを描いた画像を使う。

自己診断の実行条件:

- 初回利用時
- アプリ更新後
- 前回成功から7日以上経過した場合
- Copilot画面操作でセレクターエラーが発生した場合
- 利用者が手動で「接続を確認」を押した場合

### 9.6 モデル選択

- 特定のモデル名を必須にしない
- 設定に優先候補名を複数持てる
- モデル選択UIが見つからない場合、現在のモデルで自己診断を行う
- 自己診断に通れば処理を続行する
- 自己診断に通らなければ業務画像を送らず停止する
- モデルが処理途中で変更された可能性がある場合、次イベントで再診断する

現行の `GPT 5.6 Think deeper,Opus,Think Deeper` のような固定候補は互換用設定として残せるが、製品要件にはしない。

## 10. Copilot解析ジョブ

### 10.1 処理単位

初期実装は精度を優先し、1回のチャットで1操作だけ解析する。

- 1操作につき2～3画像
- 操作ごとに新しいチャット
- 操作IDをファイル名とプロンプトへ入れる
- 前イベントの回答を次イベントの判断材料にしない

将来、実機評価で精度が落ちないことを確認できた場合だけ複数操作をまとめる。現行の1回6手順は廃止する。

### 10.2 状態機械

各イベントは次の状態を持つ。

```text
pending
  → evidence-building
  → preflight
  → opening-chat
  → attaching
  → waiting-upload
  → prompting
  → waiting-response
  → parsing
  → validating
  → completed

任意の処理中状態
  → retry-wait
  → 元の処理中状態

任意の処理中状態
  → needs-signin / ui-changed / service-limited / failed / cancelled
```

イベント単位で状態を原子的に保存する。アプリやPCを再起動しても、`completed` を再送せず未完了イベントから再開する。

### 10.3 再試行

| 失敗 | 自動対応 |
|---|---|
| CDP一時切断 | Edgeへ再接続し1回再試行 |
| 添付完了待ちタイムアウト | 新しいチャットで1回再試行 |
| 応答タイムアウト | 生成中か確認し、停止後に新しいチャットで1回再試行 |
| JSONがない | 修正依頼を同じチャットへ1回送る |
| JSON形式不正 | ローカル修復後、失敗なら修正依頼を1回送る |
| 候補ID不正 | 正しい候補一覧を再提示して1回再質問 |
| サインイン切れ | 自動再試行せず利用者を呼び戻す |
| UI要素不明 | 業務画像の追加送信を止め、診断情報を保存する |
| 容量・利用制限 | 待機状態とし、後から再開できるようにする |

同じ業務画像の無制限な再送を行わない。既定の最大送信回数はイベントごとに2回とする。

### 10.4 中止

- 利用者はいつでも解析を中止できる
- Copilot側で生成中なら停止ボタンを探して停止する
- 停止ボタンが見つからなくてもローカルジョブは中止できる
- 完了済み結果は残す
- 未完了イベントは `cancelled` として残し、後から再開できる

## 11. プロンプト仕様

### 11.1 基本原則

- クリックマーカーだけを確定事実として伝える
- 候補枠は機械的な候補であり、正しいとは限らないと明記する
- 画像に見えない内容を想像させない
- 操作前後の差から、手順として意味があるかを判定させる
- 最も小さい文字領域ではなく、実際に操作できる一まとまりを選ばせる
- 正しく判断できない場合は `needsReview: true` を返させる
- 出力はJSONだけに限定し、終了マーカーを付ける

### 11.2 依頼文の骨子

```text
あなたは部内向け操作マニュアルの画面解析者です。

添付画像:
- before-context: 操作直前の画面。マーカー中心が実際のクリック位置です。
- before-detail: クリック周辺。A～Hの枠は候補であり、正しいとは限りません。
- after-context: 操作直後の画面です。

行うこと:
1. この操作を手順として残す必要があるか判定する。
2. 実際に操作した最小の操作可能なまとまりを選ぶ。
3. 候補が正しければcandidateIdを返す。
4. 候補がなければcandidateIdをnullにし、クリック周辺画像に対する比率座標を返す。
5. 画面から読み取れる範囲だけで対象名、手順名、説明、補足を書く。
6. 判断できなければneedsReviewをtrueにする。

JSON以外を書かないでください。
```

現行プロンプトの「赤枠は推測ではありません」という記述は削除する。

### 11.3 回答スキーマ

```json
{
  "schemaVersion": "mb-operation-v1",
  "eventId": "event-000123",
  "keep": true,
  "actionType": "click",
  "target": {
    "candidateId": "C",
    "bbox": null,
    "label": "ファイルの選択",
    "controlType": "button"
  },
  "title": "ファイルの選択",
  "description": "［ファイルの選択］をクリックし、アップロードするファイルを指定します。",
  "note": "",
  "needsReview": false,
  "reason": "クリック後にファイル選択画面が開いているため"
}
```

`candidateId` が `null` の場合だけ、`before-detail` に対する0～1の比率座標を `bbox` へ返す。

```json
"bbox": { "x": 0.35, "y": 0.41, "width": 0.28, "height": 0.10 }
```

### 11.4 列挙値

`actionType`:

- `click`
- `rightClick`
- `input`
- `unknown`

`controlType`:

- `button`
- `link`
- `input`
- `checkbox`
- `radio`
- `tab`
- `menu`
- `menuItem`
- `listItem`
- `file`
- `folder`
- `icon`
- `canvas`
- `other`
- `unknown`

## 12. 回答のローカル検証

Copilot回答は次をすべて通過して初めて解析成功とする。

- JSONオブジェクトとして読める
- `schemaVersion` が対応版である
- `eventId` が依頼したIDと一致する
- `keep` と `needsReview` が真偽値である
- `actionType` と `controlType` が列挙値内である
- `candidateId` が実在する、または `bbox` が有効である
- `bbox` の各値が0～1で、幅と高さが正である
- 選択矩形がクリック位置を含む、または許容距離内である
- 選択矩形がウィンドウ面積の過大な割合を占めない
- 対象名が200文字以内である
- 手順名、説明、補足がプロジェクトの文字数制限内である
- 依頼していないイベントIDが混入していない

検証で切り詰める前に、文字数超過はCopilotへ一度だけ修正依頼する。再失敗時は安全に切り詰めて `needsReview: true` にする。

`keep: false` は自動削除を意味しない。確認一覧で未選択にするだけとする。

## 13. 赤枠と切り抜きの確定

### 13.1 候補が選ばれた場合

ローカルに保存した候補座標を元画像座標へ変換し、赤枠注釈として設定する。

### 13.2 自由座標が返った場合

- 詳細画像内座標から元画像座標へ変換する
- クリック位置との整合性を検証する
- 過小、過大、画面外の矩形を拒否する
- 自由座標採用時は常に `needsReview: true` とする

### 13.3 対象を決められない場合

誤った赤枠を付けず、クリック位置を示す小さなリングだけを付ける。手順は確認一覧へ残す。

### 13.4 初期切り抜き

赤枠確定後にローカルで計算する。

- 対象の周囲に文脈が残る余白を加える
- 元画像は保持する
- 極端に狭い切り抜きを避ける
- 文字が小さい場合も、ネイティブ画素を先に保持してから表示倍率を決める
- 利用者は「切り抜きを戻す」でウィンドウ全体へ戻せる

## 16. セキュリティとプライバシー

### 16.1 送信前の説明

次を明示する。

- 画像は利用者のMicrosoft 365 Copilotへ添付される
- ローカル画像のコピーはOneDriveへ保存される
- 会話は組織の保持、監査、eDiscoveryの対象になり得る
- 直接アップロード画像の内容はPurview DLPで自動検査されない
- 送れない情報がある場合は手動黒塗りまたはイベント除外を行う

### 16.2 送信先制限

- 許可ホストを設定で管理する
- 既定はMicrosoft 365 Copilotの職場向けホストだけとする
- 個人向けCopilotや不明なホストへ遷移した場合は送信しない
- URL、タイトル、サインイン状態を送信前に再確認する

### 16.3 ローカル一時ファイル

- Copilot用派生画像をジョブ専用フォルダーへ置く
- ジョブ完了または中止後に安全に削除する
- 診断画像へ業務画面を保存する場合は、利用者が開けるローカル診断フォルダーだけへ置く
- ログへ画像内容、入力文字、プロンプト全文を書かない
- ログへファイル名、イベントID、状態、エラーコードだけを残す

### 16.4 クラウド側の削除

APIがないため、アプリはCopilot会話とOneDrive上の添付コピーを確実に削除できない。削除済みと表示してはならない。

必要な場合は、利用者または組織のMicrosoft 365保持手順に従う案内を出す。

## 18. 性能要件

| ID | 要件 |
|---|---|
| P-01 | 記録中のクリック操作へ知覚できる遅延を加えない |
| P-02 | クリック前画像はクリック時刻以前100ms以内の画像を95%以上で採用する |
| P-03 | 記録停止後3秒以内に送信前確認を表示する |
| P-04 | 30操作の記録を途中中断しても再起動後に未処理分から再開できる |
| P-05 | Copilot解析中もManualBuilderの既存手順を編集できる |
| P-06 | 100操作を記録してもリングバッファが無制限に増えない |
| P-07 | Copilot用一時画像は処理後にローカルから削除される |

Copilotの応答時間はサービス側に依存するため、1操作あたりの絶対時間を合格条件にしない。実機試験では中央値、90パーセンタイル、30操作の総時間を記録し、UI上の待ち方を評価する。

## 19. 品質・受入基準

評価データは、従来方式で失敗した画面を重点的に含む100操作以上とする。

内訳の目安:

- 普段のEdge上のWeb画面: 25件
- ページ遷移が速いWeb操作: 15件
- ファイルエクスプローラー: 20件
- ファイル選択ダイアログ: 15件
- ExcelなどOffice: 15件
- 独自描画、旧式、対象不明画面: 10件
- 意味のない空クリック: 別途20件以上

### 19.1 機能受入基準

| ID | 基準 |
|---|---|
| A-01 | 記録用Edgeを起動せず、普段のEdgeとデスクトップアプリを連続記録できる |
| A-02 | ページ遷移操作の98%以上でクリック前画面が保存される |
| A-03 | 意味のある操作をAIが除外候補にする割合が2%以下である |
| A-04 | 操作対象の赤枠が実務上正しい割合が90%以上である |
| A-05 | 誤ったウィンドウ全体枠を自動確定する割合が0%である |
| A-06 | 対象を決められない場合、誤枠ではなくクリック位置へ安全に戻る |
| A-07 | 手順名と説明が画面から読み取れない内容を断定しない |
| A-08 | 同一入力でも結果が変わる可能性を前提に、全結果を確認できる |
| A-09 | 解析途中でアプリを終了しても完了済み結果と記録画像を失わない |
| A-10 | Copilot UI変更時、誤操作を続けず `COPILOT_UI_CHANGED` で停止する |
| A-11 | サインイン切れ時、業務画像を追加送信せず利用者へ案内する |
| A-12 | 手動黒塗りした範囲がCopilot用派生画像へ完全に焼き込まれる |
| A-13 | AIが不要判定したイベントも確認一覧から復帰できる |
| A-14 | 複数イベントを一括選択し、採用、除外、移動、削除できる |

### 19.2 Copilotアダプター受入基準

| ID | 基準 |
|---|---|
| C-01 | 自己診断が業務画像送信前に完了する |
| C-02 | 入力、添付、送信、回答取得の各段階を個別に診断できる |
| C-03 | 既知セレクターが変わっても意味的探索で復旧できる場合は処理を続けられる |
| C-04 | 複数の送信候補があり一意に決まらない場合はクリックしない |
| C-05 | JSON回答のID、候補、座標、文字数をローカル検証する |
| C-06 | 1イベント最大2回を超えて業務画像を再送しない |
| C-07 | 処理単位の結果を原子的に保存する |
| C-08 | 特定のモデル名が消えても自己診断に通るモデルで継続できる |

## 20. テスト計画

### 20.1 ローカル単体試験

- マウスフックが短いクリックを捕捉する
- フックコールバックが重い処理を行わない

- Copilot回答JSONの抽出、修復、拒否
- 候補IDと自由座標の検証
- 文字数超過と未知列挙値の拒否
- ジョブ再開と原子的保存
- 黒塗り派生画像の画素検査

### 20.2 合成Copilot試験

- 3ボタンの候補選択
- 小さいリンク
- アイコンだけのボタン
- 入力欄
- 表の行
- 候補なし
- 空白クリック
- 操作前後で変化なし
- モーダル表示
- ページ遷移

- Excel

## 21. 移行方針

大幅変更のため、一度に既存コードを削除せず、段階的に置き換える。

### Phase A: 評価基盤

- 新しい記録イベント形式
- クリック前リングバッファ
- 通常Edge、エクスプローラー、Officeの証拠画像収集
- 既存方式とCopilot方式を比較する評価データ作成

### Phase B: Copilotアダプター強化

- 自己診断
- 1操作1チャット
- 新プロンプトと新回答スキーマ
- 回答検証、再試行、途中再開
- UI変更診断

### Phase C: 新確認UI

- 送信前除外
- 手動黒塗り
- 解析進捗
- Copilot結果確認
- 複数選択操作

### Phase D: 既定経路切替

- 記録用EdgeをUIから削除
- 新方式を「操作を記録して手順にする」の唯一の経路にする
- DOM確定ロジックを候補生成へ格下げ
- README、要件、再確認手順を更新

### Phase E: 旧方式整理

新方式が受入基準を満たした後に、次を削除する。

- 記録用Edge起動コード
- 記録用Edgeの専用プロファイル設定
- DOM pointerdownキャッシュ
- 記録用Edge向け案内
- DOMを確定値として扱うテスト

Copilot制御用Edge、Copilotプロファイル、CDP基盤は削除しない。

## 22. 主なリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Copilot UI変更 | 全解析停止 | アダプター隔離、意味的探索、自己診断、診断ログ |
| Copilotサービス停止 | 手順化できない | 記録と解析を分離、途中再開 |
| モデル変更 | 精度変動 | 固定名に依存せず、合成自己診断、実機評価 |
| 非決定的回答 | 同一操作で結果差 | JSON契約、ローカル検証、確認画面 |
| 誤った不要判定 | 必要手順の欠落 | 自動削除せず未選択で残す、A-03で評価 |
| 誤った赤枠 | 誤解を招く画像 | 候補選択優先、自由座標は要確認、過大枠拒否 |
| 機密画像の送信 | 情報管理上の問題 | 送信前確認、手動黒塗り、許可ホスト制限 |
| 添付のOneDrive保存 | クラウドにコピーが残る | 明示説明、削除を保証しない |
| DLPが直接添付を検査しない | 自動防止できない | アプリ側確認を必須化 |
| 解析時間増大 | 待ち時間 | バックグラウンド、進捗、編集継続、中止・再開 |
| UI操作の誤クリック | 別機能を実行 | 状態検証、一意でない場合停止、ホスト制限 |

## 23. 実装開始前に確定する事項

次は仕様実装へ入る前の実機検証で確定する。

1. 1操作あたり2画像と3画像の精度差
2. クリック後画像の最適取得時刻
3. 詳細画像の最適サイズ
4. 候補最大数A～Hの妥当性
5. Copilotが自由座標を返す場合の実用精度
6. 1操作1チャットの平均処理時間
7. 標準アクセスと優先アクセスの差
8. Copilot用Edgeを画面外で動かした場合の安定性
9. 合成自己診断が実画面精度低下を検出できるか
10. OneDrive上の添付コピーに対する組織内の運用ルール

## 24. 本仕様によって変更される既存方針

本仕様は、操作記録とCopilot下書きに関して、READMEに記載されたv0.28.0～v0.34.1の次の前提を置き換える。

- UI AutomationやDOMから確定値を得る
- 赤枠を先に確定してCopilotへ渡す
- 記録用Edgeを推奨する
- 低信頼時だけ別方式へフォールバックする
- 1回のCopilot依頼で6手順を処理する
- Copilotは文章作成だけを担う

出力、編集、注釈、プロジェクト保存、Office安全要件など、操作記録以外の既存仕様は維持する。
