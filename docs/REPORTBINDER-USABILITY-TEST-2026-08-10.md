## 観察結果

### 1. 起動済みアプリを再度開くと 403 になる

起動済みの ManualBuilder に対して `run.cmd` を再実行すると、ランチャーがトークンなしの `runtime.url` を開いていた。ルート画面の認証強化後は 403 となるため、現在の `entryUrl` を優先し、厳格に検証した URL だけを開く必要がある。

### 2. 自動操作では操作イベントが 0 件になる

内蔵ブラウザーと外部 Chromium の自動操作はいずれも、OS のマウスフックではクリックとして数えられず、ライブ表示は 0 件だった。これは OS 実入力だけを証拠にする設計としては妥当だが、利用者には「入力フックは正常だが対象操作を検出できていない」ことが分かりにくい。

### 3. 0 操作から 6 件の画面差分候補を作れるが、取り込めない

外部 Chromium の試行では、0 回の操作から 6 件の画面差分候補を作成できた。確認画面で 6 件すべてを選択し、タイトルも編集できる。しかし［確認した内容で手順を作成］を押すと、サーバーが `取り込める操作証拠がありません。` と拒否した。

画面差分候補はクライアントとサーバーの双方で正式な候補として生成されているため、確認・編集・選択まで許可してから一律に拒否する現在の挙動は不整合である。このため試作マニュアルは 0 手順のままになった。

### 4. 記録開始までの導線が長い

新規マニュアルから記録開始まで、編集画面の［記録の操作画面を開く］、ダイアログ内の同名ボタン、小型操作画面の［記録を開始］という複数段階がある。初回ワーカー準備も約 20 秒かかり、準備中と操作待ちの違いをより明確に示す余地がある。

## 確定修正仕様

1. 起動済みランチャーは、現在のセッショントークンを含む `entryUrl` を最優先で開く。形式が不正な場合は開かず、トークンなし URL への安全でないフォールバックをしない。
2. 操作イベントが 0 件でも、有効な画面差分候補があり、利用者が確認画面で明示的に採用した場合は取り込みを許可する。
3. 画面差分だけの記録では、capture start/end 台帳と採用した before/after フレームをプロジェクト存続期間の証拠として保存する。操作数は 0 のまま保持し、操作があったように見せない。
4. 画面差分だけで作った手順は `要確認`、低信頼度、赤枠なしとし、ユーザーがタイトル・説明を確認した事実を変換判断へ保存する。
5. 画面差分候補を取り込めない条件が残る場合、確認画面を表示する前に理由を出し、編集後の最終操作で初めて失敗させない。
6. 0 操作 + 有効フレーム、有効操作あり、壊れた台帳、画像欠落、別セッション混入を自動テストする。

サブエージェントの独立レビューにより、クライアントから受け取った候補の証拠情報を信頼せず、サーバーで候補を再生成して ID 照合する条件を追加した。また、画面差分手順は利用者が確認画面を送信しても、取り込み後に低信頼・赤枠なし・要確認を維持する仕様へ確定した。

## 検証した自動テスト

- 通常の操作証拠取り込みと既知欠落の回帰
- 0 操作 + 有効画面差分 + 利用者確認の取り込み
- 候補オブジェクト改ざんを破棄し、サーバー再生成値だけを採用
- 不明候補 ID と未確認画面差分の副作用なし拒否
- capture-start 重複、operation 件数不一致、別セッション混入の拒否
- 画面差分証拠を含むプロジェクトの検証・再保存
- Web UI が元操作 0 件を 1 件として表示しないこと
- 配布バージョン、ランチャーキャッシュ、静的配線
